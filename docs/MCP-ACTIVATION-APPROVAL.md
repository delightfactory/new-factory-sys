التوصية: استخدام Supabase Auth الحالي للمصنع، وعميل ChatGPT عام واحد مسجل يدويًا، وPKCE S256، وعنوان HTTPS ثابت واحد لنشر MCP وواجهة الموافقة داخل مشروع Vercel الحالي. يبدأ التحقق بالقراءة، ثم تفتح بوابة الأوامر بعد نجاح الشروط أدناه ضمن الموافقة نفسها. لا يوجد حد 60 دقيقة؛ كان اقتراحًا سابقًا من المنفذ، وليس طلب أحمد.

## حدود الموافقة المطلوبة

- المشروع الحي `cgqunqczuvwfvuzlsvyy` والمستخدم أحمد الحالي `983f9ec7-eb91-4e75-b589-af261f4db8ca` فقط. الاتصال دائم حتى الإلغاء، بصلاحيات المستخدم الأصلية الفعلية دون ترقيتها. أي مستخدم أو عميل أو مورد آخر يحتاج قرارًا جديدًا.
- كشف بيانات المخزون والفواتير والمرتجعات والإنتاج والحسابات والتقارير التي يسمح بها دوره إلى ChatGPT، وتنفيذ مجموعة الأوامر المراجعة في `MCP-CAPABILITY-MATRIX.md`: الفواتير وأوامر الإنتاج والتعبئة والتجميع، الحركات المالية الداخلية، الجرد، البيانات الأساسية والتصحيحات أو الإلغاءات المدعومة. 69 أداة إجمالًا، منها 54 أداة أوامر. الإدارة المحمية/الأسرار/استعادة Auth تظل إحالات للواجهة الأصلية؛ هذا ليس ادعاء اكتمال كل سير عمل.
- تطبيق المهاجرات الأربع المراجعة بالترتيب: `20261009130620` ثم `20261009140827` ثم `20261009152500` ثم `20261009161500`. هذه تغييرات دائمة على قاعدة الإنتاج، تشمل استبدال دوال إكمال الإنتاج والتعبئة وترحيل المبيعات، ومنع تحديث الدور والنشاط مباشرة في `profiles` مع بقاء تعديل الاسم ودوال الإدارة الأصلية. لا استعادة بيانات أو حذف سجلات عند التراجع.
- تعديل ونشر `create-user` فقط بما يلائم التوقيع الجديد: إيقاف فحص JWT القديم في بوابة Edge، مع التحقق داخل الوظيفة عبر Auth.getUser، ثم اشتراط توكن أصلي محدود للجلسة الأولى وصلاحية admin نشطة. توكن MCP مرفوض. `scheduled-backup` لا يتغير. لا إنشاء مستخدم حقيقي للاختبار دون أمر منفصل.
- ضبط OAuth server ومسار الموافقة وtoken hook المراجع، والتوقيع غير المتماثل عند الحاجة. لا إلغاء مفاتيح التوقيع الحالية أو جلسات التطبيق، ولا تغيير مدة جلساته أو مفاتيح API أو DCR إلى وضع مفتوح. إذا وُجد hook قائم، يلزم التوافق معه دون استبداله بصمت.
- عميل PUBLIC واحد، `token_endpoint_auth_method=none`، grants `authorization_code` و`refresh_token`، scopes `openid offline_access` فقط؛ لا client secret. callback واحد يُنسخ حرفيًا من إدارة الاتصال في ChatGPT، بلا wildcard. المورد هو عنوان النشر الثابت `/api/mcp`، ولا يتغير بعد الموافقة والمصالحة. لا توجد هذه القيم الفعلية بعد.
- إنشاء اعتماد `factory_mcp_gateway` مقيد في قناة المالك الآمنة، بلا ملكية أو عضويات أو تجاوز RLS أو وصول مباشر للجداول؛ خمس دوال RPC محددة فقط. المالك يحفظ سلسلة الاتصال مباشرة في سر Vercel الخاص بالنشر. لا أسرار أو توكنات في الشات أو معاملات أدوات الوكيل أو ملفات محلية. لا خدمة role للمستخدم أو MCP؛ تعتمد وظيفة إدارة المستخدمين القائمة على اعتمادها الخادمي الموجود أصلًا دون نسخه.
- سياسة الوصول والعميل والموافقة تستخدم `expires_at='infinity'` بعد الموافقة فقط؛ JWT نفسه يحتفظ بانتهائه المحدود وتجديده لدى المزود، وكل طلب/تجديد يعيد فحص الدور والنشاط والجلسة وموافقة المزود والإلغاء. لا تُنشأ السياسات بهذا المستند.
- موافقة المستخدم الأصلية تصف القراءة والأوامر منذ البداية (`can_write=true` للمجموعة المراجعة)، لكن النشر يبدأ بـ`FACTORY_MCP_WRITES_ENABLED=false`. فتح البوابة بعد نجاح الشروط، بنفس المورد والعميل والموافقة، لا يحتاج حذف الاتصال وإعادة إنشائه. لا تسمح موافقة الإعداد بإجراء فاتورة أو دفع أو إكمال فعلي بلا قصد المستخدم المحدد.
- النشر المقصود MCP/الموافقة في بيئة ثابتة من المشروع الحالي، متصلة بقاعدة المصنع الحية؛ لا قاعدة staging متحققة. لا نشر الواجهة الإنتاجية أو تغيير دومين الإنتاج أو شراء خدمات. إذا لم يوفر Preview عنوانًا ثابتًا قابلًا للاستخدام الدائم، يُحسم عنوان MCP البديل قبل منح الوصول دون تبديل مورد قائم بصمت.

## شروط الانتقال إلى الأوامر ضمن الموافقة نفسها

1. إعادة قراءة catalog ومقارنته باللقطة وخطة التراجع؛ التقاط إعدادات Auth غير السرية الحالية ومراجعة التوافق. أي اختلاف مؤثر يوقف التطبيق قبل تغييره.
2. نجاح دخول وتجديد جلسة التطبيق الأصلي وقراءة profiles واستدعاءات الإدارة غير المدمرة؛ توقيع جديد لا يمنع `create-user`. لا تعديل مستخدمين حقيقيين لمجرد اختبار.
3. نجاح OAuth/PKCE والهوية والدور والموافقة وتجديد التوكن على المزود الحقيقي؛ SDK يكتشف الأدوات والقراءة ترجع الأرقام والبيانات الصحيحة.
4. رفض توكن MCP في REST/RPC/Storage/Realtime ووظيفة إدارة المستخدمين، ورفض المورد/العميل/المستخدم غير المقبول والموافقة الملغاة.
5. عند النجاح تُفتح بوابة الأوامر على نفس النشر والعنوان. أول عملية حية تكون بطلب عمل محدد من أحمد، ثم تُراجع النتيجة ورقمها والإيصال قبل التوسع. اختبارات المخزون/التكلفة/التكرار المدمرة تظل محلية؛ لا كتابة تجريبية على الإنتاج.

إذا فشلت بوابة فلا تُفتح الكتابة: يُعزل اتصال MCP وتُراجع المشكلة. لا تلقائية تفترض موافقة المستخدم، ولا توسع scopes أو roles أو grants خارج ما سبق.

## الإلغاء والتراجع

الإلغاء العادي: إلغاء سياسة المستخدم/العميل/المورد أولًا؛ هذا يمنع الطلبات التالية والتجديد، ثم إلغاء موافقة المزود وإزالة اتصال ChatGPT. يمكن تعطيل دخول البوابة وإنهاء اتصالاتها لإيقاف عام فوري، ثم إزالة سر النشر. الطلب الجاري قد ينتهي قبل الإلغاء؛ إنهاء اتصالات البوابة يوقفه مع rollback معاملته، والعمليات التي التزمت سابقًا تبقى وتُراجع بإيصالها.

التراجع عن التطبيق: اتباع `MCP-ROLLBACK-AND-COMPATIBILITY.md` و`MCP-NATIVE-ROLLBACK.sql`، واستعادة وظيفة create-user وإعدادها فقط بعد رجوع التوقيع المقبول. يحفظ التراجع بيانات الأعمال والإيصالات، ويعيد الدوال والصلاحيات الأصلية من اللقطة الحية، ويترك هياكل MCP الخاصة خاملة للأدلة. لا DROP CASCADE أو استعادة Auth أو تدوير أسرار قائم.

## سؤال الموافقة المقترح — لا يُعرض الآن

هل توافق على هذا الإعداد الدائم القابل للإلغاء لحساب أحمد والمشروع المحددين، بما يشمل المهاجرات الأربع وتعديلات SQL/صلاحيات profiles وإعدادات Auth والتوقيع ووظيفة create-user المذكورة، وعميل OAuth ومنح refresh المحددين واعتماد البوابة المقيد؛ وعلى بدء التحقق بالقراءة ثم تمكين مجموعة الأوامر المراجعة بنفس الاتصال بعد نجاح البوابات، مع بقاء كل عملية أعمال مرتبطة بقصدك وصلاحياتك؟ يدخل المالك بيانات الدخول والاعتماد ويوافق داخل القنوات الآمنة بنفسه؛ لا يتضمن ذلك نشر واجهة الإنتاج أو توسيع المستخدمين أو الوصول.

الموافقة غير مفترضة. لم تُنفذ أي تهيئة أو grant أو نشر حي. إعدادات المزود الخاصة ومفاتيح التوقيع وحالة hook الحالية تحتاج قراءة غير سرية قبل التطبيق؛ الاختبارات المحلية لا تُثبت إصدار OAuth الحقيقي.
