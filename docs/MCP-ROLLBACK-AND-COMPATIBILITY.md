## القراءة الحية ونتائج التوافق

اللقطة `MCP-NATIVE-ROLLBACK-SNAPSHOT.json` تحتوي تعريفات SQL وowners/ACL/config والسياسات فقط، دون بيانات اعتماد أو سجلات Auth. الدوال الإدارية الحالية الخمس موجودة SECURITY DEFINER بملكية postgres وتنفيذ authenticated. واجهة users-manager تستعملها للاسم والدور والنشاط وكلمة المرور والحذف؛ لا تعتمد على UPDATE مباشر للدور. create-user يستعمل getUser ثم ملف المستخدم وخادمه الأصلي لتعيين الدور. تغيير ACL المقترح لا يسحب حقوق service_role الموجودة ولا تنفيذ دوال الإدارة.

محليًا، استُخدمت تعريفات الدوال الإدارية المقروءة من الحي نفسها في قاعدة اصطناعية، مع المهاجرات الأربع: قراءة profiles وتعديل الاسم، تحديث الاسم/metadata والدور والنشاط والحذف من admin، رفض viewer والتحديث المباشر للدور/النشاط، وبقاء تعديل profile من الخادم الموجود. reset-password تمت مطابقة تعريفه وEXECUTE فقط؛ لم يُختبر تغيير كلمة مرور أو Auth Admin API الحقيقي.

AuthContext لا يتغير؛ onAuthStateChange يحدّث session/user، ويقرأ profile عند تغير user ID. hook يحفظ claims الأصلية عند الإصدار والتجديد؛ اختبار محلي يقارنها كاملة ويرفض الأمر بعد انتهاء الجلسة. تخزين profile في الواجهة قد يظل قديمًا عند تغيير الدور لنفس المستخدم؛ هذا سلوك قائم، والبوابة تفحص الدور/النشاط من DB لكل عملية. لا نعدّه إصلاحًا أو إثباتًا لدخول المزود الحقيقي.

المزود يعلن authorization_code/refresh_token وopenid/offline_access وnone. JWKS العام أعاد keys=[]؛ لا دليل على مفتاح غير متماثل جاهز. وظيفة create-user v1 مفعّل verify_jwt=true؛ scheduled-backup v1=false. التوقيع غير المتماثل قد يعطل فحص Edge القديم. التعديل المحلي يعطل فحص البوابة للوظيفة الأولى ويحتفظ بـAuth.getUser للتحقق من التوكن، ثم يرفض أي client_id/audience/resource role خاص بـMCP ويشترط admin نشط. اختُبر handler نفسه ببديل Auth API محلي: رفض غير الموثق/MCP/غير النشط/viewer، وإنشاء اصطناعي للـadmin فقط. لا يثبت ذلك GoTrue أو منصة Edge.

مصادر: https://supabase.com/docs/guides/auth/signing-keys ، https://supabase.com/docs/guides/auth/oauth-server/oauth-flows ، https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt . المقروء 2026-10-09. عدم إلغاء مفاتيح سابقة يحافظ على قبول التوكنات القديمة؛ اختبار الجلسات الحقيقي شرط فتح الأوامر.

## ما يجب التقاطه قبل أي تعديل حي

إعادة قراءة اللقطة ومقارنة SHA256/owners/ACL والـschemas/roles الجديدة: عند وجود MCP سابق أو اختلاف تعريف/صلاحية مؤثر توقف للمصالحة، ولا تعيد مهاجرة أو تكتب فوقه. catalog `supabase_migrations.schema_migrations` غير موجود في القراءة الحية؛ لا ننشئ سجلًا وهميًا أو نحذف history. manifest يحدد الملفات والتسلسل.

التقاط سجل غير سري لإعدادات Auth من واجهة المالك: OAuth enabled/DCR/consent URI؛ hook enabled/URI وإصداره إن كان موجودًا؛ algorithm/key IDs/status/current/standby/previous؛ مدة JWT/session الحالية؛ إصدار create-user وإعداد verify_jwt. لا key material أو كلمات مرور أو رموز. الأدوات الحالية لا تعرض هذه الإعدادات الخاصة دون قناة المالك؛ لا يمكن استنتاجها من discovery، ولم تُقرأ. هذه خطوة preflight لازمة قبل التطبيق، وليست مطالبة ببيانات الدخول في الشات.

تحديد عنوان HTTPS ثابت للمورد والموافقة وcallback فعلي ينسخه المالك من ChatGPT. لا Preview موجودًا الآن. لا إضافة شراء أو staging أو تغيير domain الإنتاج تحت هذه الموافقة.

## تسلسل التعافي التشغيلي

1. أوقف استقبال MCP/بوابة الكتابة. ألغِ الصفوف الخاصة بالمستخدم/العميل/المورد؛ للإيقاف العام يضبط المالك gateway NOLOGIN وينهي اتصالاته فقط. لا terminate لاتصالات التطبيق الأخرى. قبل فصل hook، عطّل أو احذف العميل المحدد لدى المزود وألغِ موافقته وgrants وجلساته، وتحقق من رفض إصدار الرموز وتجديدها؛ إلغاء سياسة الأعمال وحده غير كافٍ. ثم أزل اتصال ChatGPT. لا تعطّل OAuth عمومًا إذا ظهر مستخدم آخر مشروع. فصل hook قبل إغلاق إصدار العميل قد يعيد إصدار توكن OAuth بدور التطبيق الأصلي، ولذلك هذا ترتيب إلزامي.
2. أعد token hook enabled/URI إلى قيم preflight. يجب فصل hook قبل تعطيل دواله. لا تحذف مفاتيح أو تعيد كتابة secrets. إذا جرى تغيير التوقيع، يرجع المالك إلى المفتاح السابق غير الملغى عبر واجهة المفاتيح، مع إبقاء المفتاح الجديد مقبولًا حتى انقضاء توكناته القائمة؛ لا إلغاء شامل للجلسات.
3. استعد وظيفة create-user من `rollback/create-user/index.ts` والإعداد `verify_jwt=true` في `rollback/create-user/config.toml` فقط بعد استعادة التوقيع القديم واختبار التوافق. تشغيل الفحص القديم بينما تصدر توكنات غير متماثلة قد يبقي الوظيفة معطلة؛ لا تنفذ هذه الخطوة قبل شرطها. بيانات اعتمادها الموجودة لا تُنسخ أو تُبدل.
4. أوقف Preview الذي يحتوي الخدمات المعدلة أو أعد نسخته السابقة؛ واجهة الإنتاج لم يُطلب نشرها. شغّل `MCP-NATIVE-ROLLBACK.sql` كمالك مخوّل، بعد إعادة مطابقة اللقطة: يبطل سياسات MCP وينزع تنفيذ wrappers الجديدة، ثم يستعيد دوال الإنتاج والتعبئة والمبيعات الثلاث وصلاحيات UPDATE على profiles الأصلية. BEGIN/COMMIT وlock_timeout=5s؛ عند تعذر قفل، rollback وتنسيق نافذة إعادة المحاولة، لا قتل جلسات أخرى.
5. تحقق من التعريفات/owners/ACL والسياسات وقراءة ملف المستخدم وتجديد جلسة أصلية. ابق schemas/receipts/snapshots الجديدة خاملة؛ لا DROP CASCADE أو استعادة بيانات مالية/مخزون/Auth. الإيصالات والعمليات التي التزمت تُحفظ ولا تُحذف. إعادة صلاحيات baseline تعيد الاتساع الأصلي أيضًا؛ توثيق ذلك جزء من قرار recovery، لا claim لتحسين أمان baseline.

اختبار التراجع المحلي قارن pg_get_functiondef للدوال الثلاث باللقطة الحية، وفحص UPDATE ورفض بوابة MCP، وأثبت بقاء أمر إنتاج وإيصال قائم. خطة Auth تراجع إعدادات المزود من snapshot preflight؛ لا يمكن اختبار تبديل مفاتيح المزود محليًا، وهو gate حي مشروط.
